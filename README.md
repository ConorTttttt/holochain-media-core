# Holochain Media Core

Reusable, file-type-independent content contracts and security interfaces for Holochain Music, Video, and future applications.

**Status: CORE-005 technical milestone / pre-release (not production).** The workspace verifies Holochain Music S1 signed manifests and receipts (CORE-002), stores verified ciphertext in a resumable content-addressed store (CORE-003), binds Holochain identity, discovery and certificate-pinned MoQ retrieval to that store (CORE-004, real five-conductor acceptance suite), and verifies Music's signed streaming grants and personal licences against Holochain-authenticated owners and listeners (CORE-005). It does **not** encrypt files, issue grants, unwrap content keys, approve publications, serve public media, or accept payments. A CORE-005 `Authorized` result is a policy decision: the application must still unwrap the key (AES-GCM authenticated) before plaintext access. See docs/CORE-005-entitlement-verification.md and docs/CORE-004-holochain-moq-integration.md. S2 key-binding v2 (proof of possession, opt-in separate v2 storage DNA; explicit `BindingAssurance` levels) is described in docs/S2-KEY-BINDING-V2.md. S2 key lifecycle v2.1 (rotation, recovery, revocation with explicit `KeyValidity`, host-attributed `replica-receipt/v2`; opt-in separate v2.1 storage DNA) is described in docs/S2-KEY-LIFECYCLE-V21.md.

## Boundaries

- **Holochain:** signed identity, validated discovery and durable application metadata. No media payloads and no plaintext content keys on the public DHT.
- **Content Core:** immutable package/manifest contracts, provenance verification, storage integrity, access policy and lifecycle interfaces (introduced incrementally).
- **MoQ/QUIC:** peer-to-peer encrypted-content transport and ephemeral live streams. It is not an authorisation service.
- **Storage peers:** opaque ciphertext objects, signed receipt assertions and future availability/repair.
- **Music / Video:** codecs, playback, transcoding, creator interfaces and application-specific presentation.

The first implementation reuses Music's existing package/receipt formats through compatibility tests; it will **not** rewrite or silently migrate existing user data.

## Build

Requires a stable Rust toolchain with Cargo, rustfmt and Clippy.

    cargo fmt --all -- --check
    cargo clippy --workspace --all-targets -- -D warnings
    cargo test --workspace --all-targets

CI runs those checks on pull requests (also with `--features serde_json/preserve_order`). The real-service suite (Holochain conductors + MoQ hosts) runs locally; see docs/CORE-004-holochain-moq-integration.md. This repository has **not** been validated on a physical two-device network.

## Compatibility and migration

Music uses the signed wrapper and canonical JSON serialization in its Python module holochain_storage/package.py. CORE-002 verifies golden vectors generated by that code at a pinned commit; CORE-005 does the same for Music's `content-grant/v1` and `personal-licence/v1` (81 cases). Music has an opt-in, disabled-by-default comparison adapter (holochain_storage/media_core_adapter.py; `check_access` added on its CORE-005 branch); no production read/write, grant, unwrap, playback or export path was switched. Existing grants and licences remain valid. Video is unchanged.
